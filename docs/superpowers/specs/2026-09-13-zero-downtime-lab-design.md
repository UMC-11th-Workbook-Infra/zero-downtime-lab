# zero-downtime-lab 설계

작성일: 2026-09-13

## 1. 목적

배포하는 동안 요청이 실제로 유실되는지, 얼마나, 몇 초 동안 유실되는지를 챌린저가 눈으로 확인하게 하는 로컬 도구다.

챌린저는 노트북에서 `docker compose up` 한 번 하고 `localhost:9376` 을 연다. 폼에 자기 앱의 회원가입 API 규격을 넣고 시작을 누른 뒤, 평소대로 배포한다. 배포가 끝나면 화면에 순단 구간이 `14:32:07부터 3.4초, 68건 실패` 형태로 찍혀 있다.

curl 을 세면서 눈대중하는 것을 대체하는 것이 이 도구의 존재 이유다.

## 2. 범위

### 하는 일

- 대상 앱에 고정 레이트로 요청을 계속 쏜다
- 요청 1건마다 성공/실패와 소요 시간을 기록한다
- 실패 건수를 유형별로 집계한다
- 응답 지연의 백분위수와 임계값 초과 건수를 집계한다
- 연속 실패 구간을 순단으로 자동 감지해 목록에 띄운다
- 실시간 그래프로 초당 성공/실패와 지연을 그린다
- 실행 결과를 JSON 으로, 시나리오를 k6 스크립트로 내보낸다

### 하지 않는 일 (명시적 비범위)

| 항목 | 이유 |
|---|---|
| 배포 트리거 | 배포는 챌린저가 자기 방식대로 한다. 이 도구는 관측만 한다 |
| 테스트 데이터 정리 | 대상 앱 구조에 따라 너무 달라진다. 랩이 관여할 영역이 아니다 |
| Prometheus / Grafana | 해상도가 맞지 않고 (4.6 참고), 설정 입력을 받지 못한다. 관측 챕터에서 별도로 다룬다 |
| 부하테스트 (램프업, 한계점 탐색) | 측정 목적이 다르다. 부하테스트 챕터에서 k6 로 별도 구성한다 |
| 인증, 다중 사용자, 영속 저장 | 노트북에서 혼자 쓰는 도구다 |

### 제약

대상 앱은 외부 호스팅(IP 또는 도메인)이고 관측 스택은 노트북에서 돈다. 노트북과 대상 사이 인터넷 구간의 노이즈는 제거할 수 없다. 이 설계는 노이즈를 없애는 대신 **구분 가능하게** 만든다 — 실패를 유형별로 나누고(4.4), 배포 전 베이스라인과의 델타로 읽게 한다(4.7).

## 3. 구조

컨테이너 하나에 웹 서버와 프로버가 같이 들어간다. 빌드 단계가 없어야 `docker compose up` 이 가볍게 유지되므로, 프론트엔드는 번들러 없이 바닐라 JS 로 작성하고 차트 라이브러리는 로컬에 벤더링한다.

```
[브라우저 설정 폼] ──POST /api/runs──> [Node 백엔드]
                                          │
                                          ├─ Prober: 고정 레이트로 대상에 요청
                                          │   └─ 레코드 { ts, status, durationMs, outcome, failureType }
                                          │        │
                                          │        ├─> Bucketer      (1초 집계)
                                          │        ├─> OutageDetector (순단 감지)
                                          │        └─> Baseline      (초기 구간 기준값)
                                          │
[브라우저 대시보드] <──SSE 스트림────────┘
```

### 3.1 단위와 경계

각 단위는 하나의 일만 하고, 레코드 스트림이라는 하나의 인터페이스로 연결된다.

| 단위 | 하는 일 | 의존 |
|---|---|---|
| `Scheduler` | 응답과 무관하게 고정 간격으로 발사 신호를 낸다 | 없음 |
| `RequestTemplate` | 플레이스홀더를 치환해 실제 요청 바디를 만든다 | 없음 |
| `classify` | 응답 또는 예외를 outcome/failureType 으로 분류한다 | 성공 판정 설정 |
| `SequenceBuffer` | 완료 순서로 도착한 레코드를 발사 순서로 되돌린다 (4.2) | 없음 |
| `InternalProber` | 위 넷을 엮어 레코드를 뱉는다 | Scheduler, RequestTemplate, classify, SequenceBuffer |
| `Bucketer` | 레코드를 1초 버킷으로 접는다 | 없음 |
| `OutageDetector` | 레코드 스트림에서 순단 구간을 잡는다 | 없음 |
| `Baseline` | 초기 구간의 기준 실패율과 p95 를 계산한다 | 없음 |
| `RunStore` | 실행을 메모리에 보관한다 (최근 10건) | 없음 |
| `k6Exporter` | 시나리오 설정을 k6 스크립트 문자열로 만든다 | 없음 |

`Bucketer`, `OutageDetector`, `Baseline`, 대시보드는 레코드 스트림에만 의존한다. 레코드를 **누가** 만드는지는 알지 못한다.

### 3.2 Prober 인터페이스

이것이 나중에 k6 를 붙일 수 있게 하는 유일한 장치다.

```js
// prober/index.js
// Prober: 시나리오를 받아 요청 레코드를 흘려보내는 것
//
//   start(scenario, onRecord) -> Promise<void>   실행이 끝나면 resolve
//   stop() -> void                               즉시 중단
//
// 레코드 형태:
//   { seq, ts, status, durationMs, outcome, failureType, error }
```

현재 구현체는 `InternalProber` 하나다. 나중에 `K6Prober` 를 추가하면 k6 서브프로세스의 JSON 출력을 같은 레코드 형태로 변환하기만 하면 되고, 대시보드와 분석 단위는 수정하지 않는다. `K6Prober` 는 지금 만들지 않는다.

## 4. 측정 설계

측정의 정확성이 이 도구의 전부이므로, 아래 네 가지를 명시적으로 정의한다.

### 4.1 고정 레이트 발사 (coordinated omission 회피)

**응답을 기다린 뒤 다음 요청을 보내면 안 된다.** 대상이 배포 중 죽어 응답이 없을 때 요청 속도가 같이 죽어버려서, 정작 측정해야 할 구간의 표본이 사라진다. 유실을 재는 도구가 유실 구간에서 눈을 감는 셈이다.

`Scheduler` 는 `1000 / rps` ms 간격으로 in-flight 여부와 무관하게 발사한다. 대상이 5초간 응답하지 않아도 그 5초 동안 `rps × 5` 건이 나가고 전부 타임아웃 실패로 기록된다.

in-flight 가 무한히 쌓이지 않도록 상한을 둔다: `rps × (timeoutMs / 1000) × 2`. 상한을 넘으면 발사를 건너뛰고 `dropped` 로 센다. `dropped` 가 0 이 아니면 화면에 경고를 띄운다 — 그 실행의 수치는 신뢰할 수 없다는 뜻이다.

### 4.2 레코드 순서 복원

요청은 발사 순서대로 나가지만 **완료 순서는 뒤집힌다.** 배포 중 상황을 그려보면 왜 문제인지 분명해진다.

| 요청 | 발사 | 완료 | 결과 |
|---|---|---|---|
| A | 0.00초 | 5.00초 | 타임아웃 |
| B | 0.05초 | 5.05초 | 타임아웃 |
| C | 3.10초 | 3.15초 | 성공 (대상 복구됨) |

완료 순서대로 순단 감지에 넣으면 `C(성공) → A(실패) → B(실패)` 가 된다. 연속 실패 구간이 성공으로 잘려서 순단이 아예 안 잡히거나 엉뚱한 위치에 잡힌다. 타임아웃이 길수록 더 심해지는데, 하필 타임아웃이 길어지는 상황이 바로 측정하려는 그 구간이다.

그래서 레코드를 **발사 순서로 재정렬한 뒤** 집계·순단 감지에 넘긴다. 스케줄러가 실제로 발사한 요청에만 `seq` 를 빈틈없이 붙이므로(버린 슬롯은 `seq` 를 소비하지 않는다), 시간 창을 두고 기다리는 대신 `seq` 연속성만으로 정확하게 복원할 수 있다.

레코드의 `ts` 도 완료 시각이 아니라 **발사 시각**이다. 순단의 지속 시간은 "요청을 보냈는데 안 되던 구간"이지 "응답이 늦게 온 구간"이 아니다.

### 4.3 성공 판정

성공은 **사용자가 정한 상태코드 목록에 포함되는가** 로만 판정한다. 회원가입은 앱에 따라 `200`, `201` 이 갈리고, 중복 이메일에 `409` 를 주는 앱도 있다. 랩이 정할 문제가 아니므로 폼에서 받는다.

기본값은 `[200, 201]`.

### 4.4 실패 분류

인터넷 구간 노이즈와 앱 장애를 구분하기 위해 실패를 네 갈래로 나눈다.

| 유형 | 조건 | 읽는 법 |
|---|---|---|
| `network` | DNS 실패, 커넥션 거부/리셋, TLS 실패 | 배포 중이면 인스턴스 교체 신호, 평상시면 회선 노이즈 |
| `timeout` | `timeoutMs` 초과 | 대상이 살아있지만 응답 못 하는 상태 |
| `server` | 5xx | 앱이 떠 있으나 처리 실패 |
| `client` | 4xx 중 성공 목록 밖 | 대개 설정 실수. 시작 직후 다수 발생하면 폼 설정을 의심 |

화면에서 이 넷을 분리해서 보여준다. 배포 중에만 `network` 와 `timeout` 이 치솟는 것이 전형적인 유실 패턴이다.

### 4.5 지연 집계 대상

두 지표 모두 **응답을 받은 요청만** 대상으로 한다. 응답이 없는 `network` 와 `timeout` 실패는 제외한다.

타임아웃을 `timeoutMs` 값으로 쳐서 백분위수에 섞으면 p99 가 타임아웃 설정값에 붙어버려 실제 응답 지연이 보이지 않는다. 응답이 아예 없었다는 사실은 백분위수가 아니라 실패 건수와 순단이 말해준다.

- **백분위수 (p50/p95/p99)**: 응답을 받은 모든 요청 (성공 + 4xx + 5xx)
- **지연 임계값 초과 건수 (`slow`)**: 성공한 요청 중 `durationMs > slowThresholdMs` 인 것

`slow` 를 성공 요청으로만 한정하는 이유는, 실패한 요청이 느린 것은 이미 실패 건수에서 세고 있기 때문이다. `slow` 가 답해야 하는 질문은 "성공은 했는데 사용자가 기다렸는가" 다.

### 4.6 순단 감지

Prometheus 를 쓰지 않는 이유가 여기 있다. 스크랩 간격 15초 격자에 3초짜리 공백을 그리면 점 하나가 살짝 내려앉고 끝이다. 순단은 집계된 시계열이 아니라 개별 요청의 타임라인에서만 보인다.

**정의:** 연속 실패 레코드가 `minConsecutiveFailures` (기본 3) 건 이상 이어진 구간.

단발 실패 1~2건은 순단으로 치지 않는다. 인터넷 구간 노이즈를 걸러내기 위한 값이고, 기본 20 rps 에서 3건은 약 150ms 에 해당한다.

**지속 시간:** 순단 직전 마지막 성공의 `ts` 부터 순단 이후 첫 성공의 `ts` 까지. 실패 레코드의 시작과 끝이 아니라 성공과 성공 사이의 간격을 재는 것이 사용자가 체감하는 실제 단절 시간이다.

실행이 끝날 때까지 성공이 돌아오지 않으면 순단은 열린 상태로 두고 `진행 중` 으로 표시한다.

실행 시작부터 한 번도 성공한 적이 없는 상태에서 실패가 이어지는 경우는 순단으로 치지 않는다. 끊긴 것이 아니라 애초에 닿은 적이 없는 것이고, 이 경우는 8장의 자동 중단이 처리한다.

**출력:** `{ startTs, endTs, durationMs, failureCount, byType }`. 총 다운타임은 모든 순단의 `durationMs` 합계다.

### 4.7 베이스라인

시작 후 첫 `baselineSec` (기본 30) 초를 평상시 구간으로 잡아 실패율과 p95 를 기록한다. 이후 모든 수치를 이 기준과의 델타로 같이 보여준다 — `평소 0.2% → 배포 중 100%`.

인터넷 구간 노이즈가 남아 있어도 절대값 대신 델타로 읽으면 유실 판정이 선명해진다.

베이스라인 구간 자체의 실패율이 5% 를 넘으면 화면에 경고를 띄운다. 배포를 시작하기 전에 이미 뭔가 잘못됐다는 뜻이므로, 그 상태로 측정해도 의미가 없다.

## 5. 시나리오 설정

웹 폼이 만들어내는 형태다. 폼이 유일한 입력 경로이고, 설정 파일을 직접 편집할 일은 없다.

```json
{
  "name": "회원가입 유실 측정",
  "target": {
    "url": "https://api.example.com/users/signup",
    "method": "POST",
    "headers": { "Content-Type": "application/json" },
    "body": "{\"email\":\"lab-{{uuid}}@test.local\",\"password\":\"Test1234!\",\"nickname\":\"u{{counter}}\"}",
    "timeoutMs": 5000
  },
  "success": { "statusCodes": [200, 201] },
  "load": { "rps": 20, "durationSec": 300 },
  "analysis": {
    "slowThresholdMs": 1000,
    "baselineSec": 30,
    "minConsecutiveFailures": 3
  }
}
```

### 플레이스홀더

회원가입은 같은 값으로 두 번 부르면 두 번째가 실패하므로, 매 요청 고유한 값이 필요하다. 바디와 헤더에서 치환된다.

| 토큰 | 치환 결과 |
|---|---|
| `{{uuid}}` | UUID v4 |
| `{{counter}}` | 실행 내 요청 일련번호 (1부터) |
| `{{timestamp}}` | 발사 시각 epoch ms |
| `{{random}}` | 8자리 영숫자 |

접두어를 `lab-` 처럼 붙이도록 폼 기본값과 안내 문구를 잡는다. 나중에 대상 앱에서 테스트 데이터를 지울 때 기준이 된다. 지우는 것 자체는 이 도구의 일이 아니다.

## 6. API

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| POST | `/api/runs` | 시나리오를 받아 실행 시작, `runId` 반환 |
| POST | `/api/runs/:id/stop` | 실행 중단 |
| GET | `/api/runs/:id/stream` | SSE. `bucket` / `outage` / `summary` / `state` 이벤트 |
| GET | `/api/runs/:id` | 실행 요약 |
| GET | `/api/runs` | 최근 실행 목록 (최대 10건) |
| GET | `/api/runs/:id/export.json` | 결과 요약 JSON 다운로드 |
| GET | `/api/runs/:id/export.k6.js` | 시나리오를 k6 스크립트로 다운로드 |
| GET | `/api/health` | 컨테이너 헬스체크 |

동시에 실행 가능한 run 은 하나다. 이미 실행 중일 때 `POST /api/runs` 는 409 를 반환한다.

### SSE 이벤트

```
event: bucket    { tsSec, sent, success, failure, byType, slow, p50, p95, p99, maxMs }
event: outage    { startTs, endTs, durationMs, failureCount, byType, ongoing }
event: summary   { totals, percentiles, baseline, outages, downtimeMs, dropped }
event: state     { status: "running" | "stopped" | "finished", error }
```

`bucket` 은 1초마다, `summary` 는 5초마다와 종료 시점에 보낸다.

## 7. 화면

한 페이지다. 상단이 설정, 하단이 결과.

**설정 영역** — 실행 중에는 비활성화된다. URL, 메서드, 헤더(키-값 여러 줄), 바디(플레이스홀더 도움말 포함), 성공 상태코드, RPS, 지속 시간, 그리고 접어둔 고급 설정(타임아웃, 지연 임계값, 베이스라인 길이, 최소 연속 실패 수).

**결과 영역**

| 구역 | 내용 |
|---|---|
| 요약 타일 | 총 요청, 실패 건수(유형별 분리), 순단 횟수, 총 다운타임, p95 지연, 지연 임계값 초과 건수. 각각 베이스라인 대비 델타를 병기 |
| 그래프 | 초당 성공/실패 스택 막대 + p95 지연 라인. 순단 구간은 배경 음영으로 표시 |
| 순단 목록 | `14:32:07부터 3.4초, 68건 실패 (timeout 61, network 7)` |
| 경고 배너 | `dropped > 0`, 베이스라인 실패율 5% 초과, `client` 실패 비율이 높을 때 |

**내보내기** — 결과 JSON 다운로드, k6 스크립트 다운로드.

### 7.1 k6 스크립트 내보내기

챌린저가 이 랩에서 자기 앱의 회원가입 API 규격을 이미 맞춰놨으므로, 부하테스트 챕터에서 그것을 처음부터 다시 쓰게 하지 않는다. 폼 설정을 그대로 k6 스크립트로 뽑아 그 챕터의 출발점으로 삼는다.

생성되는 스크립트는 URL, 메서드, 헤더, 바디(플레이스홀더는 k6 문법으로 변환), 성공 판정 `check`, 실패율 0% `threshold` 를 포함한다. 부하 프로파일은 이 랩의 고정 레이트를 그대로 옮기되, 램프업으로 바꾸라는 주석을 단다.

## 8. 오류 처리

| 상황 | 처리 |
|---|---|
| 폼 URL 이 잘못된 형식 | 시작 전 검증, 폼에 인라인 오류 |
| 대상에 처음부터 전혀 닿지 않음 | 성공이 한 건도 없는 상태에서 첫 10건이 모두 `network` 실패면 자동 중단하고 "대상에 닿지 않습니다" 안내. 그대로 5분을 돌리는 것은 시간 낭비다. 한 번이라도 성공한 뒤의 연속 실패는 순단이므로 이 규칙을 적용하지 않는다 |
| `client` 실패가 베이스라인 구간에서 50% 초과 | 실행은 계속하되 "폼 설정을 확인하세요" 경고 배너 |
| SSE 연결 끊김 | 각 이벤트에 `id:` 로 버킷 순번을 실어 보낸다. 브라우저가 재연결하면 `Last-Event-ID` 헤더가 오므로, 서버는 그 이후 버킷만 다시 보낸다 |
| 서버 재시작 | 실행 기록은 메모리에만 있으므로 사라진다. 문서에 명시한다 |
| 대상이 리다이렉트 응답 | 따라가지 않는다. 3xx 는 성공 목록에 없으면 실패로 분류된다 |

## 9. 테스트

`OutageDetector`, `Bucketer`, `Baseline`, `classify`, `RequestTemplate` 은 순수 함수 단위라 합성 레코드 스트림으로 전부 검증한다.

| 대상 | 확인할 것 |
|---|---|
| `OutageDetector` | 연속 실패 2건은 순단이 아니고 3건은 순단이다. 지속 시간이 성공과 성공 사이 간격으로 계산된다. 실행 끝까지 복구 안 되면 `ongoing` 이다. 순단이 연달아 둘이면 둘로 분리된다 |
| `classify` | 성공 목록에 `409` 를 넣으면 409 가 성공이 된다. 타임아웃과 커넥션 거부가 서로 다른 유형이 된다 |
| `RequestTemplate` | `{{uuid}}` 가 매 요청 다르다. `{{counter}}` 가 1부터 순증한다. 치환자가 없는 바디는 그대로 나간다 |
| `Scheduler` | 응답이 오지 않아도 발사 간격이 유지된다. in-flight 상한에 걸리면 `dropped` 가 증가한다 |
| `SequenceBuffer` | 완료 순서가 뒤집혀 들어와도 발사 순서로 나온다. 구멍이 있으면 채워질 때까지 붙잡는다 |
| `Baseline` | 베이스라인 구간 이후 레코드는 기준값에 반영되지 않는다 |
| `k6Exporter` | 생성된 스크립트가 `k6 --version` 이 아니라 Node 파서로 구문 검증을 통과한다 |

**통합 테스트 (이 도구의 핵심 검증):** 로컬에 테스트 서버를 띄우고, 프로버를 돌리는 도중 서버를 3초간 죽였다 살린다. 순단이 정확히 1건 감지되고 지속 시간이 3초 ± 허용오차 안에 들어오는지 확인한다. 이 테스트가 통과하지 못하면 도구 전체가 의미 없다.

## 11. 구현 메모

- 포트는 `9376` 을 쓴다. 8080 은 챌린저 노트북에서 이미 다른 것이 물고 있을 확률이 높다. `9376` 은 등록된 서비스가 없고, Kubernetes 공식 문서의 Service 예제에 쓰이는 번호라 인프라 워크북 맥락에도 맞는다. 호스트 포트는 `docker-compose.yml` 에서 `PORT` 환경변수로 바꿀 수 있게 한다
- 런타임은 Node 20 이상. 빌드 단계를 두지 않는다
- 차트는 uPlot 을 로컬에 벤더링한다. 오프라인에서도 동작해야 한다
- UI 작업 시 전역 지침에 따라 `emil-design-eng` 스킬을 먼저 적용한다. 이 프로젝트는 자체 디자인 시스템이 없다
- `README.md` 에 다음을 명시한다: 실행 기록은 메모리에만 남는다, 테스트 데이터 정리는 챌린저 책임이다, 노트북과 대상 사이 네트워크 노이즈가 있으므로 델타로 읽어야 한다

## 12. 나중 챕터와의 연결

| 챕터 | 이 랩과의 관계 |
|---|---|
| 부하테스트 | `export.k6.js` 로 뽑은 스크립트에서 출발한다. 램프업 시나리오와 단계별 임계치는 그 챕터에서 k6 로 작성한다 |
| 관측 | k6 에 내장된 Prometheus remote write 출력으로 `k6 → Prometheus → Grafana` 를 별도 compose 프로파일로 구성한다. 정확한 플래그 이름은 그 시점의 k6 버전 기준으로 확인한다 |

이 랩 안에 Prometheus 와 Grafana 를 미리 깔아두지 않는 이유는, 그것을 직접 붙여보는 것이 관측 챕터의 실습 내용 자체이기 때문이다.
